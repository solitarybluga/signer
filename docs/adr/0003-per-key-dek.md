# ADR-0003：每密钥独立 DEK，KEK 信封包裹

- 状态：已接受
- 日期：2026-10-20

## 背景

单层方案让同一个对称密钥既加密所有私钥，又参与 Shamir 分片。这样实现简单，但有两个问题：加密密钥轮换时需要重新加密全部私钥；一把密钥的加密参数暴露范围过大，没有按密钥隔离。

信封加密把“数据密钥”和“保护数据密钥的密钥”分开：DEK 只加密单个私钥，KEK 只负责包裹 DEK，并且是参与门限分片的那把密钥。

## 决策

- 每个私钥生成一个独立的随机 DEK（32 字节，来自操作系统 CSPRNG）。
- 私钥用 DEK 以 XChaCha20-Poly1305 加密。
- DEK 用 KEK 以 XChaCha20-Poly1305 包裹。
- KEK 随机生成，通过 Shamir 秘密分享拆给份额持有者；解封时重建。
- 存储中保存：私钥密文、DEK 密文、两个 AEAD nonce，以及公钥和元数据。
- v0.1 不使用 Argon2id：DEK 与 KEK 都是随机密钥，不涉及口令派生。后续如增加口令保护，再引入 Argon2id。

## 备选方案

| 方案 | 不采用的原因 |
| --- | --- |
| 单层 KEK 直接加密所有私钥 | 轮换需全量重加密，缺少按密钥隔离 |
| 每密钥一个 KEK 并分别分片 | 份额管理成本成倍增加 |
| KEK 托管在 HSM/KMS | 可作为后续演进，但 v0.1 不引入外部依赖 |

## 影响

- 正面：轮换 KEK 时只需重新包裹所有 DEK，不需要重新加密私钥。
- 正面：单个 DEK 泄露只影响一把密钥；按密钥隔离更清晰。
- 正面：KEK 仍是门限解封的唯一敏感点，信任边界不变。
- 负面：每条密钥记录多出两个字段和一次解包操作。
- 负面：解包后的 DEK 是否缓存、缓存多久，需要单独决定（见待决问题）。
