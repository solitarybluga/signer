# ADR-0002：先做门限解封，后做门限签名

- 状态：已接受
- 日期：2026-10-20

## 背景

保护签名密钥有两种相关但不同的设计：

1. **门限解封（密钥托管）。** 私钥用对称密钥（KEK）加密；KEK 通过 Shamir 秘密分享拆给独立参与方。启动时达到阈值的参与方提供份额，重建 KEK，解密私钥，之后由单个进程独立签名。Vault 的 seal/unseal 流程就是同一模式。
2. **门限签名（MPC/TSS）。** 签名私钥本身拆成份额，由多个独立签名方交互产出签名；私钥全程不重组。Ed25519 对应 FROST，ECDSA 对应 CGGMP21。

方案 1 更简单、协议面更小，适合作为第一个里程碑。方案 2 的安全模型更强：单个 signer 被攻破时既不能签名，也无法泄露私钥。

## 决策

- v0.1 只实现门限解封。
- 文档与命名必须称为“密钥托管 / 门限解封”，不得称为 MPC 或门限签名。
- v0.3 在同一套签名 API 之后加入真正的门限签名：Ed25519 用 FROST，ECDSA 用 CGGMP21。

## 影响

- 正面：可以尽早交付可审计的服务；解封层与存储模型在更换签名后端后仍然可用。
- 正面：安全取舍是显式的，便于评审和讨论。
- 负面：解封后完整私钥在单进程内存中，运行时被攻破或内存被 dump 即泄露；这一点已写入威胁模型。
- 负面：后续迁移到真正的 TSS 需要新的签名会话、份额管理与协调逻辑；存储 schema 需要提前预留。
