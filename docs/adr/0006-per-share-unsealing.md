# ADR-0006：门限签名采用 per-share 解封，每个 signer 的运维独立

- 状态：已接受
- 日期：2026-10-20

## 背景

v0.3 计划引入真正的门限签名（FROST / CGGMP21）。届时私钥不再重组，签名份额分别由多个独立 signer 持有，每个 signer 由不同的运维团队运营。

一个关键问题是：门限解封在门限签名版本里还有没有位置？如果继续使用全局 KEK，解封一次就能获得所有份额，等于把 TSS 退化成单点；这与 [ADR-0005](0005-kms-vs-threshold.md) 拒绝“KMS 单独解封”的原则相同。

但每个 signer 的运维人员不同，这提供了一种可行的边界：**每个 signer 只解封自己的份额**。

## 决策

- 每个 signer \(i\) 独立保护自己的签名份额 `share_i`，使用各自的 `KEK_i`。
- `KEK_i` 由该 signer 所属组织的运维人员做 Shamir 分片，阈值 `t_i / n_i` 由该组织决定。
- 解封只发生在 signer \(i\) 本地；解出的 `share_i` 不离开该 signer，优先放入本地 HSM/KMS，或仅在进程内存中短暂存在。
- **不存在全局 KEK**，也不存在能一次解开所有份额的恢复密钥。
- 签名仍然需要达到签名阈值 `t / n` 个 signer 在线并执行 TSS 协议；per-share 解封只负责每个 signer 的启动授权。
- 签名密钥必须通过 DKG 生成或由可信仪式生成后销毁完整私钥；不能存在知道完整私钥的 dealer。

## 信任模型

```text
Org A 运维 t_A-of-n_A → KEK_A → share_A（signer A）
Org B 运维 t_B-of-n_B → KEK_B → share_B（signer B）
Org C 运维 t_C-of-n_C → KEK_C → share_C（signer C）

签名：t-of-n 个 signer 通过 FROST / CGGMP21 协作
```

安全不变量：

1. 任一组织持有的签名份额数量必须小于签名阈值 `t`，避免单组织作恶或失陷即达到门限。
2. 任一组织被攻破最多泄露自己的 `share_i`，无法单独签名。
3. 没有任何参与方可以解封超过一个份额。
4. 解封阈值不等于签名授权；即使某个 signer 完成解封，也不能绕过 TSS 协议。
5. 备份、恢复和密钥轮换不得重新引入能解开所有份额的全局密钥。

## 运行流程

### 启动

1. signer \(i\) 以 sealed 状态启动，只持有自己的加密份额和 `KEK_i` 的份额校验材料。
2. 该组织的运维人员按 `t_i` 提供 `KEK_i` 的 Shamir 份额。
3. signer \(i\) 在本地重建 `KEK_i`、解密 `share_i`，然后擦除 `KEK_i` 和份额明文，仅在 HSM/内存中保留 `share_i`。
4. 写入审计事件（组织、时间、参与的运维人员标识，不记录份额内容）。

### 签名

- 达到签名阈值 `t` 的 signer 共同执行 FROST / CGGMP21。
- 未解封或离线的 signer 不参与，签名会话按协议失败或重试。

### 轮换与人员变更

- 运维人员变化时，重新对该组织的 `KEK_i` 做 Shamir 分片。
- 签名密钥按 TSS 协议做 proactive refresh，避免长期使用同一组份额。

## 备选方案

| 方案 | 结论 |
| --- | --- |
| 全局 KEK 包裹所有 TSS 份额 | 拒绝：解封一次即集中所有份额，破坏 TSS |
| 全局 KMS 托管 KEK | 拒绝，理由见 ADR-0005 |
| 每个组织用本地 KMS/HSM 保护 `KEK_i` | 接受，可作为 per-share 解封的加强版 |
| 完全不做解封，份额直接由本地磁盘保护 | 可行但启动授权较弱；per-share 解封提供更明确的组织级审批 |
| 单组织运维所有 signer | 拒绝：组织隔离消失，退化为单点信任 |

## 影响

- 正面：没有单一服务、管理员或云账号能解开全部份额，信任边界与组织边界一致。
- 正面：一个 signer 的失陷只影响一个份额，签名门限仍然有效。
- 正面：解封作为启动授权，与签名协议解耦，职责清晰。
- 负面：每个组织都要维护自己的解封仪式、运维人员和审计，运营成本随组织数增长。
- 负面：某个组织凑不齐 `t_i` 时该 signer 不可用，可能影响签名可用性。
- 负面：没有全局恢复密钥；组织丢失份额后的恢复策略必须提前定义，且不能演变成新的单点。
- 负面：需要 DKG、份额轮换和跨组织审计等额外工程。
