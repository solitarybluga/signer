# ADR-0004：使用 sqlx 作为数据库访问层

- 状态：已接受
- 日期：2026-10-20

## 背景

signer 的存储只有三张核心表（`keys`、`unseal_sessions`、`audit_log`），但要求强一致、显式事务和可审计的 SQL。服务基于 tonic 异步栈，需要同时支持 PostgreSQL（集群）与 SQLite（单机演示）。

候选方案：

- **sqlx**：异步 SQL 工具包，不是 ORM；支持两种后端、内置迁移、编译期 SQL 校验。
- **SeaORM**：基于 sqlx 的异步 ORM，实体和关系映射方便，但增加抽象层。
- **Diesel**：类型安全成熟，但以同步为主，异步需要 diesel-async。
- **rbatis**：动态 SQL，生态成熟度一般。

## 决策

- 采用 **sqlx**，不引入全功能 ORM。
- 存储层继续收在 `KeyStore` trait 后面，提供 `PostgresStore` 与 `SqliteStore` 两个实现。
- 查询使用显式 SQL。v0.1 使用运行时 `query` / `query_as`；schema 稳定后，关键查询切换到 `query!` / `query_as!`，并提交 `.sqlx/` 离线缓存供 CI 使用。
- 迁移使用 `sqlx::migrate!`，按方言分目录维护：`migrations/postgres/`、`migrations/sqlite/`。
- 事务、行锁、advisory lock 直接写 SQL；不依赖 ORM 隐式行为。

## 备选方案

| 方案 | 不采用的原因 |
| --- | --- |
| SeaORM | 对这个 schema 偏重；行锁、审计等仍需原生 SQL，抽象收益有限 |
| Diesel | 同步模型与 tonic 异步栈不匹配，diesel-async 增加复杂度 |
| rbatis | 生态与成熟度不足，安全审计成本更高 |
| tokio-postgres / rusqlite | 更底层，没有迁移与编译期校验，维护成本更高 |

## 影响

- 正面：SQL 完全可见，便于安全评审与性能分析。
- 正面：同一套 trait 覆盖单机与集群两种后端；迁移与校验工具链齐全。
- 正面：审计日志、唯一约束、行锁等可直接表达。
- 负面：需要手写映射代码，没有实体关系带来的开发便利。
- 负面：两种方言的差异（UUID、JSONB、TIMESTAMPTZ、advisory lock）需要分别处理；SQLite 只支持单写者。
- 负面：编译期校验依赖数据库或离线缓存，CI 需要维护 `.sqlx/`。
