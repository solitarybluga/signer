# ADR-0005：v0.1 不用 KMS 托管 KEK，保留门限信任模型

- 状态：已接受
- 日期：2026-10-20

## 背景

当前设计是每密钥一个 DEK、部署级 KEK 信封包裹 DEK，KEK 通过 Shamir 分片交给多个持有者，启动时达到阈值才能解封。

另一种常见方案是把 KEK 放进 KMS。这个方案有一个直接的疑问：**如果 KEK 都能交给 KMS，为什么不把所有签名私钥也交给 KMS/HSM？** 这个疑问是成立的：一旦 KMS 能解包 KEK，KMS 就成为唯一信任根，信封加密只剩“减少 KMS 调用、轮换便宜”的工程收益，安全模型上并不比 KMS 直接持有私钥更强。

因此需要明确：KMS 和门限解封不是可以随意叠加的两层，而是两种不同的信任模型。

## 决策

- v0.1 **不引入 KMS 托管 KEK 或签名私钥**，继续使用 Shamir 门限解封。
- 不允许“KMS 单独解封”的混合形态：如果 KMS 能在没有份额持有者参与的情况下释放 KEK，门限模型即失效。
- 未来如接入 HSM/KMS，选择一种独立模式，而不是把 KMS 塞进现有解封层：
  1. **直接托管模式**：签名私钥放在 HSM/KMS，signer 只调用签名接口；放弃自定义信封和门限解封。
  2. **份额保护模式**：KMS 只保护每个持有者的份额或持有者私钥，解封仍需达到 Shamir 阈值。
- 记录 HSM/KMS 为路线图中的独立部署模式，不作为 v0.1 的内部组件。

## 为什么

- **信任模型一致性**：门限方案的价值在于“任何单一参与方都无法解封/签名”。KMS 是单点授权，二者混用会出现最弱环节。
- **曲线支持**：主流 KMS 对 secp256k1、Ed25519 的支持有限；EVM 和 Solana 场景往往需要 CloudHSM 或 MPC，而不是普通 KMS。
- **密钥不可导出**：KMS 托管的密钥通常无法导出，带来厂商锁定；对多链、多环境部署要提前评估。
- **信封加密的收益有限**：KMS 托管 KEK 时，DEK 分层主要降低调用次数和轮换成本，不改变信任根。
- **直接托管确实更简单**：如果产品目标是单点托管和低运维成本，HSM/KMS 直接签名通常代码更少、密钥边界更清晰，应作为一个完整模式来评估。

## 备选方案

| 方案 | 结论 |
| --- | --- |
| KMS 托管 KEK，应用继续管理 DEK/私钥 | 不采用：KMS 成为单点信任根，与门限叙事冲突 |
| KMS/HSM 直接持有签名私钥，signer 调用签名 API | 可作为未来独立模式；需评估 secp256k1/Ed25519 支持与成本 |
| KMS 只保护每个持有者的份额/私钥 | 可作为混合演进；解封仍需阈值，信任模型不退化 |
| 当前 Shamir 门限解封 | v0.1 采用 |

## 影响

- 正面：v0.1 的信任模型保持自洽：没有单一服务或管理员能单独解封。
- 正面：不引入云厂商依赖，便于本地、私有化和多环境部署。
- 负面：需要运维份额持有者和解封仪式，运营成本高于托管方案。
- 负面：解封后 KEK 在进程内存中，运行时被攻破的风险依然存在，见威胁模型。
- 后续：真正的门限签名（FROST / CGGMP21）与 KMS 托管是两条独立演进路线，不能互相替代。
