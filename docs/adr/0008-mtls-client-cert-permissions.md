# ADR-0008：mTLS + 客户端证书权限位掩码

- 状态：已接受（已实现）
- 日期：2026-10-23

## 背景

v0.1 的 gRPC 没有 TLS、客户端认证和授权，只适合本机或可信网络。`ImportKey` 也因为缺少安全传输一直返回 `UNIMPLEMENTED`。

服务重启会丢失内存中的 KEK，必须重新走门限解封。因此新增客户端或调整权限不能依赖“改本地配置 + 重启”，也不能依赖一个运行时可写的授权策略文件：

- 本地策略文件热加载意味着谁能写文件谁就能提权；
- 指纹/客户端白名单放在 `signer.toml` 里，新增或撤销客户端都要改配置并重启；
- 外部授权服务或 JWT/OIDC 能解决动态授权，但会引入额外服务、网络依赖和可用性要求。

本项目是开源项目，不能假设部署方的 CA 支持 SPIFFE、SPIFFE 之外的 URI 约定、Certificate Policies 或自定义扩展。

## 决策

1. **传输层使用标准 mTLS**：
   - tonic 0.14 + `tls-ring`（rustls/ring）。
   - 服务端证书 `serverAuth`；客户端证书 `clientAuth`。
   - `client_ca_path` 接受任意 PEM CA bundle；不假设特定 CA 产品。

2. **授权信息放在客户端证书里**：
   - `URI:signer://principal/<actor>`：恰好一个，审计 actor。
   - `URI:signer://holder/<holder-id>`：零个或多个，用于 `SubmitUnsealShare` 绑定。
   - `URI:signer://permissions/0x<16-hex>`：最多一个 u64 权限位掩码；缺失视为 0。

3. **权限位**：
   - bit 0–7 已分配并实现：`unseal.start`、`unseal.submit`、`unseal.status`、`unseal.seal`、`key.create`、`key.import`、`key.read`、`key.sign`。
   - bit 8/9 预留给未来的 `key.destroy`/`audit.read`，在对应 RPC 实现前也必须为 0。
   - bit 10–63 保留，必须为 0。
   - 任何保留位为 1（含 bit 63、全 1 mask）都拒绝整张证书；不做忽略、通配或“未来权限自动生效”。
   - mask 0 表示无权限，不表示全部权限。
   - 位号只追加，不重排、不复用；新增权限必须先升级 signer，再签发新证书。
   - 拒绝保留位而不是忽略，原因：
     - 未知授权语义必须 fail closed，避免跨版本“潜伏权限”：旧证书在未来 bit 被分配后突然获得新权限；
     - `0xFFFF...`/模板默认全 1 会变成当前所有权限的 god mode，即使只忽略未知位也会保留所有已知危险位；
     - 17 位以上 hex 若被截断会改变权限语义，必须拒绝而不是静默截断；
     - 保留位为 1 通常表示 CA 模板与 signer 版本不匹配，应立即暴露升级顺序错误；
     - 审计必须能准确说明证书被授予了什么，不能接受无法解释的授权数据。
   - 类比 X.509 critical extension：验证方不认识 critical extension 时必须拒绝整张证书。

4. **服务端只保留静态权限表**：
   - 没有 `[authz]` 策略文件，没有热加载，没有按客户端的指纹白名单。
   - 每个 RPC 在产生副作用前检查一个固定 permission。
   - `CreateKey` / `Sign` 的审计 actor 来自证书 principal。
   - 明文模式保留为本地开发默认；启动时 warn。

5. **CA 是授权根**：
   - CA 必须在签发时强制校验权限位；否则客户端可以自行申请 `unseal.seal`/`key.sign`，模型失效。
   - 本版不实现 CRL/OCSP，也不维护本地 deny list；撤销依赖短有效期证书和 CA 流程。
   - 服务端证书或 CA bundle 轮换仍需重启并重新门限解封。

## 备选方案

| 方案 | 结论 |
|---|---|
| 指纹/客户端白名单放 `signer.toml` | 拒绝：新增/撤销客户端要重启，重启丢失 KEK |
| 本地授权策略文件热加载 | 拒绝：可写授权根 = 提权路径；原子替换/签名只能缓解 |
| 外部授权服务（OPA/Cedar） | 备选：动态角色最灵活，但增加服务、网络和可用性依赖；本版不引入 |
| JWT/OIDC scope | 备选：适合已有 IdP 的部署；增加 token 获取、绑定和撤销复杂度；本版不引入 |
| 证书内角色 + 服务端角色→权限表 | 备选：语义更结构化，但角色定义变化仍需 signer 发版；位掩码更直接 |
| 证书内权限位掩码 | **采用**：一个 u64 字段直接表达方法集；新增客户端/改权限只重签证书 |
| 自定义扩展承载权限列表 | 备选：语义更自由，但需要自定义 ASN.1/schema，CA 支持面更窄；SAN URI 更通用 |
| 按角色拆分客户端 CA | 备选：不需要解析证书属性，但角色多时 CA 数量膨胀，多角色客户端难处理 |

## 影响

- 正面：
  - 新增客户端、更换证书、调整权限只影响 CA 签发，不重启 signer、不重新解封；
  - 没有本地可写授权数据，减少提权面；
  - 权限位是 CA 签名的，审计 actor 和权限来源清晰；
  - 每个 RPC 独立权限，支持发起解封、提交份额、只读、签名、创建私钥分离。
- 负面：
  - CA 必须能签发 SAN URI 且能强制权限模板；不支持时需要自定义扩展 fallback；
  - 改权限要重新签发证书；
  - 没有本地 deny list/CRL/OCSP，撤销依赖短有效期和 CA；
  - 新增权限位需要 signer 发版，且必须“先升级服务端、再签发新证书”；
  - 权限位是长期协议，位号不能重排/复用。
- 安全：
  - CA 私钥或签发流程被攻破等价于全部权限被攻破；
  - 证书被窃后在有效期内仍可用；
  - mTLS 不替代 Holder Ed25519 签名、nonce 绑定和 VSS 校验；
  - 明文模式仍只适合本机/可信网络。

## 兼容性

- `[tls]` 缺失时保持现有明文行为，现有客户端和测试不受影响。
- 启用 `[tls]` 后，旧的无证书客户端会在握手或应用层被拒绝；这是有意的 breaking change。
- 未使用策略文件，因此没有旧授权配置需要迁移。
- `ImportKey` 仍为 `UNIMPLEMENTED`；mTLS 落地后再单独实现。
